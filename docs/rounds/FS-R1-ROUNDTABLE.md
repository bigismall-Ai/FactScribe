> 席位：外部红队（mcode CLI）／内部红队（实现层）／蓝队／主持（编排）
> 靶子：`DESIGN-v2.md`（用户给定）→ 产出 `SPEC-V2.1.md`

## 一、这一轮的判决

**红队（外部，22 条）总攻**：v2 是一份**意图声明**，不是可落地规范——大量"禁止/必须/收敛"缺少可执行判据，且 §4 自己把最关键的五个问题列为开放问题。
**红队（内部，17 条）补刀**：现有实现已经在"漏红"——`10/16` 能把 `1/16` 判绿（四舍五入白名单）、`\tableinput` 是审计隧道、`\pkignore` 能包整句假结论、`\todoq` 真的把 `PENDING:` 印进 PDF。

**蓝队裁决**：39 条全覆盖——采纳 31／部分 7／驳回 1（驳回：内部 S5「CI 必须带产物快照」的原命题，与 §2.1「facts 只读」冲突，改为在 `release` 阶段要求）。

## 二、定下来的四条硬判据（v2.1）

| # | 判据 | 解决的红队条目 |
|---|---|---|
| **D1** | `\fact{id}` = **句级绑定单元（BU）**：以标记切段，段内**每个**数字 token 必须落在该 fact 的**显式值域**里；删掉四舍五入白名单，`10/16 → 1/16` 必红 | 内部 B2/B3、外部 R-B3/R-S1 |
| **D2** | **审计集 = 从 `main.tex` 递归可达的全部 `.tex`**；纯 `\input` 包装宏自动展开；表格必须带生成 spec／cell map，不许当隧道 | 内部 B1、外部 R-B5/R-S2 |
| **D3** | **L0（静态，无 runs/ 也能跑）／L1（有 runs/ 的送达性校验）／L2（CI 全量）** 三层；`UNVERIFIED ≠ PASS`；阻断力下沉到 `release`/stamp，而不是逼团队关掉 `--strict` | 外部 R-B1/R-B8、内部 S4 |
| **D4** | **送达性证据层**＝run record（`request_body_sha256`／`response_sha256`／`delivered`／`tool_call_count`）；facts 的观测必须指向 run record，工具校验"账上观测"与"run record 的 payload 摘要"一致 | 外部 R-B8、R-B2 |

**诚实边界（写进 SPEC，不藏着）**：D4 只能证明"账上引用的 payload 与被记录的 payload 一致"，**不能证明它真的发出去过**；同一 agent 若同时伪造 runs/ 与 facts，仍可自洽。信任根仍是人签。

## 四、下一轮（R2）请重点打这三点

1. **闭包规则能不能被"宏展开"绕过**：`\newcommand{\body}{...}` 定义在 `main.tex`、内容在正文里被调用——审计集只扫文件，能不能扫到"渲染后才出现"的文字？
2. **D1 的句级 BU 在真实段落里会不会大面积误报**：一个句子同时引用两个 fact 怎么办？一条 fact 的 `display` 与 `value` 不一致时以谁为准？
3. **D4 的 run record 由谁写**：如果由同一个 agent 写，是不是又回到"同源自证"？人签在什么粒度上才不形同虚设？
