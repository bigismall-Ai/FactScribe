# SPEC-BRIEF｜写作简报：从账里生成起草依据（批 126）

状态：批 126 冻结（实施依据）。
范围：新增 `factscribe brief` 子命令与模块 `factscribe/brief.py`；
不改 `facts` / `terms` / `config` / `audit` / `style` 的既有判据与退出码；
零第三方依赖（纯标准库）。

一句话：**`brief` 把「写这篇论文草稿要遵守的全部约束」从账里生成成一份
Markdown，交给写作模型当依据；它不判断文字好坏，只把账里的可用材料与红线
摆齐。**

---

## 1. 与既有命令的分工

| 命令 | 时点 | 干什么 | 不干什么 |
|---|---|---|---|
| `brief` | 起草**前** | 把项目名、节结构、可用事实、术语正名、硬约束、验收命令装成一份写作依据 | 不改稿、不扫文风、不判红黄 |
| `polish` | 已有文字**后** | 扫 `style` 的命中，按处方出「改什么、不许动什么」的工作单 | 不提供新的事实或数字 |
| `audit` | 交稿**前** | 核验每个数字是否绑定到账上的 fact、每条引用是否落地，判红/黄/绿 | 不告诉模型该怎么写 |

三条命令共用同一批账：`facts/*.toml`、`terms/paper.tsv`、`sections/*.tex`、
`style`/`audit` 的验收口径。`brief` 只读账，不产生新的判据与新的数字。

**起草 vs 润色**：`brief` 面向「从零写一节」，`polish` 面向「已有句子怎么改」。
两者可以串起来用——先按 `brief` 起草，再用 `polish` 的处方收紧文风，最后用
`audit` + `review` 验收——但谁都不替代谁。

---

## 2. 命令

```text
python3 -m factscribe brief <项目目录> [--section <前缀>] [--out <文件>] [--json]
```

| 参数 | 必填 | 语义 |
|---|---|---|
| `project` | 否 | 项目目录，默认当前目录；必须有 `paperkit.toml` 与至少一条 fact |
| `--section` | 否 | 只出某一节的简报：按节文件名词干前缀匹配（例 `04`）；给空串或匹配不到任何节即用法错（exit 2） |
| `--out` | 否 | 把 Markdown 写到文件（目录不存在则创建）；给了就不同时往 stdout 写正文 |
| `--json` | 否 | stdout 只出 JSON；与 `--out` 可同时使用 |

退出码沿用既有分层：成功 `0`；配置/用法错 `2`；工具内部错误 `4`。
本命令不是闸门：不存在「红」「黄」「绿」三种成功码。

## 3. 五节定义（结构冻结）

输出是 Markdown，固定五节，节标题逐字为：

```text
## 1. 写作任务
## 2. 可用主张与数字
## 3. 术语表
## 4. 硬约束
## 5. 验收
```

### 3.1 写作任务

- 项目名（取 `paperkit.toml` 的 `name`，没有则 `title`；不打印路径）；
- 主文件（`root_tex`；没有 `root_tex` 时为 `main.tex`；再没有则说明按文件名排序）；
- 节清单：按主文件 `\input` / `\include` 的**出现顺序**；主文件不存在时按
  `sections/*.tex` 的**文件名排序**；
- 每节给三项：相对文件名、当前标题、**该节已有事实条数**。

「当前标题」取该文件第一个 `\section`/`\subsection` 等标题命令（复用 `style`
的标题抽取）；没有标题的文件写 `（无标题）`。

「该节已有事实条数」＝该文件里 `\fact{ID}` 绑定到的**不同** fact id 数
（复用 `texscan.scan_tex` 的 markers），不是全项目账的条数。

### 3.2 可用主张与数字

逐条列出 `id / claim / value`，一条不漏；表头下第一条提示写明：
正文必须用 `\fact{id}` 绑定，id 与下表逐字一致。

**只列 claim 与 value，不列 `source` / `locator` / `source_sha256`**——这是给
写作看的材料，不是审计报告。编造数字与「改了数字但绑定旧 id」都会被 `audit`
拒绝，所以写作时只许从这张表取数。

### 3.3 术语表

来自 `terms/paper.tsv`（项目根有 `glossary.tsv` 时以项目表为准，与 `style`
同一解析顺序）。逐条列出：正名（canonical）、类别、可用别名、**禁用变体**
（`blocked(cn)` 列）。表前写明「同一概念全篇只用正名」。

### 3.4 硬约束

五条固定红线，逐字输出：

1. 不许编数字：正文每个数字都必须来自 §3.2 并绑定 `\fact{id}`；
2. 标题不带冒号、问号、句号（行内标题除外）；
3. 不用插入式破折号（`——` / `—`）；
4. 术语首次出现要在首句解释；
5. 不写「首先／其次／最后」式排比。

这五条是**写作纪律**，不是新判据；对应的机械检查仍由 `style` / `audit`
承担。

### 3.5 验收

给出两条命令的调用形（用占位符，不写死绝对路径）：

```bash
python3 -m factscribe audit <项目目录> --build
python3 -m factscribe review --before <改前目录> --after <改后目录>
```

并写明：**红＝不许交（退出码 1 打回）；黄＝要人看（退出码 3 不阻断，但必须
逐条过人眼）；绿＝退出码 0 才算可以交。**

## 4. 节过滤（`--section`）

`--section 04` 时：

- **节清单**只留文件名词干以 `04` 开头的节；
- **事实**按 fact id 前缀过滤（大小写不敏感）：id 以 `04` 开头的才入表；
- 账里的 fact id 通常不以节前缀命名（真实项目里是 `B1`、`S3a` 这类），
  因此**过滤不到任何一条时全列**，并在**文首**用引用块写明：
  「本节简报的事实无法按 id 前缀 `04` 过滤，故全列 N 条」；
- 术语表与硬约束、验收不随节过滤（全篇一致，节与节不能各用一套正名）。

过滤后没有任何节文件即用法错（exit 2），不输出空简报。

---

## 5. 确定性与安全

- 同输入两跑**逐字节一致**；不写时间戳、不写绝对路径、不读随机源；
- 事实顺序＝账本装载顺序（`facts/*.toml` 排序后按文件内顺序）；
- 术语顺序＝词表行序；节顺序＝主文件 `\input` 顺序或文件名排序；
- 表格单元格里的 `|` 转义成 `\|`，换行压成空格；
- 只读项目文件，不写项目目录（`--out` 写的路径由调用方指定）。

## 6. 失败面（不输出空简报冒充成功）

| 情形 | 退出码 | 说明 |
|---|---|---|
| `paperkit.toml` 缺失/坏 | 2 | 既有 `ConfigError` |
| 一条 fact 都没有 | 2 | 「facts 为空……简报无从生成」 |
| 一个节文件都没有 | 2 | 「sections 为空……没有可写的节」 |
| `--section` 空串或匹配不到节 | 2 | 点名给的前缀 |
| 词表读不了 | 2 | 既有 `ConfigError` |

**空简报不许当成功**：没有事实就没有「可用主张与数字」，起草依据不完整，
必须报错让人先补账。

## 7. 与 `audit` 的关系

`brief` 是**写作输入**，`audit` 是**交稿判卷**。二者的唯一共同点是从同一批账
读同一个事实集合：

- `brief` 把 fact 的 `claim` / `value` 原样交出，不推导、不换算、不补全；
- `audit` 独立核验正文里每个数字的绑定与值域；
- 写作模型若在 `brief` 之外自造数字，`audit` 必红；若把 `value` 改了小数位，
  `audit` 按值域判红或黄。`brief` 不替 `audit` 做任何预先判定。
