# 批 17：MiniMax 从 0/14 到 5/5——哪一刀真正救了它

- 日期：2026-11-06｜模型：MiniMax-M3.1-Flash（官方 `api.minimax.cn/v1`，用户钥匙）｜题：#408 官方题面
- 脚手架不变：preflight → 写手 → 落盘 → 独立验收；只改「上下文与闸门」

## 二、三个真结论

1. **提示词管方向，闸门管停手。**
   同一批约束写进 system 后模型完全无视（0/3）；改成用户消息逐轮提醒，它才开始动手（提补丁）；
   再改成装配侧强制收口，才稳定通过。**靠模型自觉的约束等于没有约束。**

2. **定位卡以前根本没送达。**
   `request["locator"]` 写了、装配单上有 45 token 的小节，但 `build_messages` 从不读它——
   F13–F19 的请求原文里搜不到 `_asciidoc_row`。修好后首读 4/4 落在 `_asciidoc_row` 附近。

3. **降本来自“停手”，不是“压缩”。**
   同一模型：25 轮 60 万 → 15–22 轮 **15.3 万**。省下的全是“反复读、反复改”的无效轮次。

## 四、代价与保留

- 只验一道题（单文件 3000 行）；多文件未测；
- n=5，且所有批次都在同一天、同一钥匙，供应商侧波动未知；
- MiniMax 每轮输出仍是 deepseek 的 2–3 倍（8–9k vs 3–5k），换模型省不了这个；
- 机械交卷＝**最多两版补丁**：若第一版方向错、第二版也救不回，就会判死（当前样本里没出现）。

## 五、要落成什么（待签）

1. `locator` 必须进 system（已修，属 bug 修复，非新法）；
2. 进程约束：进 `plan.toml`，且**关键项必须有机械执行面**（轮次提醒、两版收口）；
3. 长程档：份额 45%、窗口 32k、token 上限 60 万——三项已有实测依据，待签。
